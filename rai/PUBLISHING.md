# Публикация RAI на GitHub

Через веб-интерфейс, без единой команды git. Три файла перетащить в форму
релиза — и у всех пользователей появится обновление.

---

## Настроено один раз

В `package.json` уже указано:

```json
{
  "author": "wfllive-official",
  "license": "MIT",
  "repository": {
    "type": "git",
    "url": "https://github.com/wfllive-official/rai"
  }
}
```

Адрес зашивается в собранный `.sh` — проверка обновлений смотрит именно туда.

---

## Каждый выпуск: 3 шага

### 1. Записать изменения в CHANGELOG.md

**Единственное место, где задаётся версия.** Добавьте раздел сверху:

```markdown
## 3.1.0

- исправлена ошибка подписи release-сборок
- ускорена проверка проекта перед сборкой
```

Для важного обновления — пометка:

```markdown
## 3.1.1 [важное]

- исправлена критическая ошибка
```

Тогда у пользователей уведомление станет заметнее:

```
▲ Важное обновление: RAI v3.1.1  (у вас 3.1.0)
  исправлена критическая ошибка
```

### 2. Собрать

```bash
npm run build:debug
bash build/debug/rai-debug.sh status      # проверить, что работает

npm run build:release
```

Сборщик сам:

- прочитает версию и заметки из `CHANGELOG.md`
- обновит `package.json`
- создаст `version.json` с контрольной суммой
- проверит, что в `README.md` не просочился номер версии

```
OK  версия 3.1.0 из CHANGELOG.md
OK  version.json (v3.1.0) — в build/release/ и в корне
OK  README.md: версии внутри нет — править перед релизом не нужно
```

**README трогать не надо.** Файл всегда называется `rai.sh`, ссылка на
скачивание постоянная, а значок версии GitHub подставляет сам.
Если вы всё же впишете туда номер версии, сборка предупредит.

В `build/release/` окажутся ровно три файла:

```
rai.sh                основной файл
rai.sh.sha256         контрольная сумма
version.json          манифест обновлений
```

Сборки прошлых версий удаляются автоматически.

### 3. Создать релиз на GitHub

**Releases → Draft a new release**

| Поле | Значение |
|---|---|
| Choose a tag | `v3.1.0` → **Create new tag** |
| Target | `main` |
| Release title | `RAI v3.1.0` |
| Attach binaries | перетащите **все три файла** из `build/release/` |

Нажмите **Publish release**. Готово.

> **Главное:** `version.json` обязательно приложите к релизу.
> Именно его читают установленные копии, чтобы узнать о новой версии.

## Где что задаётся

Чтобы не искать по файлам:

| Что | Где | Правится вручную? |
|---|---|---|
| Версия | `CHANGELOG.md` — заголовок `## 3.1.0` | ✅ да |
| Список изменений | `CHANGELOG.md` — пункты под заголовком | ✅ да |
| Важность | пометка `[важное]` в заголовке | ✅ да |
| `package.json` → version | — | ❌ обновляется сам |
| `version.json` целиком | — | ❌ создаётся сборкой |
| SHA-256 | — | ❌ считается сборкой |
| Дата публикации | — | ❌ ставится сборкой |
| Имя файла релиза | всегда `rai.sh` | ❌ не меняется никогда |
| Версия в `README.md` | её там нет | ❌ ничего не правится |
| Контакты, инструкция | `README.md` | ✅ да, когда нужно |

Один файл на правку вместо трёх.

## Почему коммитить не нужно

RAI ищет манифест по адресу:

```
https://github.com/wfllive-official/rai/releases/latest/download/version.json
```

GitHub сам перенаправляет `latest` на актуальный тег. Проверено на живом
репозитории:

```
302 -> https://github.com/cli/cli/releases/download/v2.96.0/...
```

Опубликовали релиз — ссылка сразу указывает на него. Ни `git push`,
ни правки ветки не требуется.

Файл `.sh` скачивается тем же способом, поэтому **имя тега не критично**.
Даже если поставите `3.1.0` вместо `v3.1.0`, обновление найдёт файл.

### Запасной источник

Если `version.json` к релизу не приложен, RAI посмотрит в ветку:

```
https://raw.githubusercontent.com/wfllive-official/rai/main/version.json
```

Оба способа рабочие. Через релиз проще — коммит не нужен.

## Что увидит пользователь

Уведомление при обычной работе:

```
$ rai list
  Constructor    v1.0 (code 1)  SDK 37  APK 1

  ▲ Доступна RAI v3.1.0  (у вас 3.0.0)
    rai update  — обновиться
```

Само обновление:

```

  файл  : rai.sh

  • проверка обновлений через version.json
  • автоустановка при первом запуске
```

## Что внутри version.json

Создаётся сборщиком автоматически:

```json
{
  "version": "3.1.0",
  "published": "2026-07-28",
  "file": "rai.sh",
  "sha256": "3454632499950bc9e115e2e2feb0fbf6b53c8b219e56aa7b96fb3b2c25a2528c",
  "minNode": 18,
  "notes": ["проверка обновлений через version.json"],
  "critical": false
}
```

| Поле | Зачем |
|---|---|
| `version` | сравнивается с установленной |
| `file` | какой файл скачивать из релиза |
| `sha256` | сверяется после загрузки |
| `minNode` | не даст обновиться на несовместимом Node |
| `notes` | из `CHANGELOG.md`, показывается пользователю |
| `critical` | делает уведомление заметнее |

## Важное обновление

Если в версии критическое исправление:

```bash
RAI_CRITICAL=1 npm run build:release
```

В манифест попадёт `"critical": true`, и уведомление станет другим:

```
▲ Важное обновление: RAI v3.1.1  (у вас 3.1.0)
  исправлена ошибка подписи release-сборок
  rai update  — обновиться
```

---

## Почему version.json, а не GitHub API

| | GitHub API | version.json |
|---|---|---|
| Лимит | 60 запросов в час без токена | нет |
| Скорость | ~200 мс | ~120 мс |
| Формат | навязан GitHub | свой: `notes`, `minNode`, `critical` |
| Зависимость | от структуры релизов | от одного файла |

Замерено на живых запросах: `api.github.com` — 0.196 с,
`raw.githubusercontent.com` — 0.117 с.

---

## Защита от подмены

Проверок две:

1. **SHA-256 из манифеста** — сверяется со скачанным файлом
2. **Самопроверка `.sh`** — внутри зашит хеш полезной нагрузки

Проверено на практике: подменил код внутри опубликованного файла,
`version.json` не трогал —

```
FAIL контрольная сумма не совпала
  ожидалось: bc9044f66e32363b5eeb34d07276ef9ad3d090865f46b729c9f50db91adb50b1
  получено : b9db92e8d8e96d87c2e664549b05cbcced505de8780e49b15902bd1b15000a09
  Файл повреждён или подменён. Установка отменена.
```

## Оформление страницы релиза

Сборщик печатает готовый текст. Рекомендуемый вид:

```markdown
## RAI v3.1.0

Один файл. Ни npm, ни распаковки.

### Установка

    curl -LO https://github.com/wfllive-official/rai/releases/latest/download/rai.sh
    bash rai.sh

Первый запуск установит команду `rai` автоматически.

### Обновление

    rai update

### Проверка подлинности

    sha256sum rai.sh
    # значение из rai.sh.sha256

    bash rai.sh --verify

### Что нового

- проверка обновлений через version.json
- автоустановка при первом запуске

### Поддержка

Только для официальных сборок. Приложите вывод `rai report`.
Для форков и модификаций обращайтесь к их авторам.
```

## Частые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `version.json не найден` | не приложен к релизу | прикрепить файл |
| Пользователи не видят обновление | забыли `version.json` | перевыпустить с ним |
| `загрузка не удалась` | `.sh` не приложен к релизу | прикрепить файл |
| `контрольная сумма не совпала` | `.sh` пересобран после манифеста | собрать заново и приложить оба |
| `нужен Node.js 18+` | `minNode` выше версии у пользователя | обновить Node |
| Обновление видно с задержкой | кэш GitHub ~5 минут | подождать |

## Если всё-таки хочется автоматизации

Для тех, кто работает через git — `.github/workflows/release.yml`:

```yaml
name: release
on:
  push:
    tags: ['v*']

permissions:
  contents: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm run build:release

      - name: Проверка
        run: bash build/release/rai-*.sh --verify

      - uses: softprops/action-gh-release@v2
        with:
          files: |
            build/release/rai-*.sh
            build/release/rai-*.sh.sha256
            build/release/version.json
          body_path: CHANGELOG.md
```

Тогда выпуск сводится к:

```bash
npm version patch --no-git-tag-version
git commit -am "v3.0.1" && git tag v3.0.1 && git push --tags
```

Но при публикации через веб-интерфейс это не нужно.
